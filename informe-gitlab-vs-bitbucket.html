1. Introducción, objetivos y metodología

1.1 Introducción

El control de versiones es la práctica que permite registrar, recuperar y auditar cada cambio realizado sobre el código fuente de un proyecto. Git es hoy el sistema de control de versiones distribuido dominante, pero Git por sí solo no resuelve dónde se aloja el repositorio, quién puede modificarlo, cómo se revisan los cambios ni cómo se prueban y despliegan automáticamente. De esa necesidad surgen las plataformas de versionamiento en la nube, entre las que destacan GitHub, GitLab y Bitbucket.

Este informe se concentra en las dos últimas. Aunque ambas alojan repositorios Git y ofrecen revisión de código y pipelines de integración continua, responden a filosofías muy distintas: GitLab se concibe como una plataforma DevOps integral que puede sustituir a varias herramientas y autoalojarse con paridad de funciones, mientras que Bitbucket es un servicio de alojamiento de repositorios profundamente integrado con el ecosistema de Atlassian (Jira, Confluence, Compass).

1.2 Objetivos

Objetivo general. Investigar y comparar las plataformas GitLab y Bitbucket, y demostrar mediante ejemplos prácticos sus ventajas y desventajas relativas.

Objetivos específicos.

  • Definir qué es cada plataforma, su origen, su modelo de licenciamiento y su arquitectura de funcionamiento.
  • Identificar las características principales de cada una, así como sus planes y precios vigentes.
  • Construir un proyecto de software de prueba y ejecutarlo dos veces: una con el flujo de trabajo y el pipeline de GitLab y otra con el de Bitbucket, manteniendo constante el código de la aplicación.
  • Documentar las salidas reales de las ejecuciones como evidencia.
  • Contrastar los resultados y formular recomendaciones de elección según el contexto de uso.

1.3 Metodología

La investigación combinó tres actividades:

  1. Revisión documental y de fuentes web oficiales (documentación técnica de GitLab y de Atlassian, páginas de precios, manual del producto y análisis de terceros de 2026), realizada el 24 de octubre de 2026. Las cifras de precios se contrastaron entre páginas oficiales, detectándose inconsistencias que se señalan en el capítulo correspondiente.
  2. Construcción de un proyecto de software común. Se desarrolló NotasApp, un módulo Python de cálculo de notas académicas con validaciones, encapsulamiento y una batería de 16 pruebas unitarias ejecutables sin dependencias externas. El mismo código se utilizó en las dos demostraciones, de modo que cualquier diferencia observada provenga de la plataforma y no de la aplicación.
  3. Ejecución de dos flujos de trabajo completos (uno por plataforma) sobre repositorios Git reales: rama corta de trabajo, confirmaciones, detección de un error por las pruebas automatizadas, corrección, fusión con commit de integración, etiquetado de versión y publicación en un servidor remoto. En cada caso se incluyó el archivo de configuración de CI/CD propio de la plataforma (.gitlab-ci.yml y bitbucket-pipelines.yml) y se verificó su validez sintáctica.
Limitación declarada de la demostración El entorno de trabajo utilizado para elaborar este informe no disponía de cuentas en GitLab.com ni en Bitbucket.org. Por lo tanto, las demostraciones se ejecutaron sobre repositorios Git locales que replican fielmente el flujo de trabajo de cada plataforma (ramas, commits convencionales, fusiones con --no-ff equivalentes al Merge Request / Pull Request, etiquetas y push a un servidor remoto simulado). Los archivos de configuración de CI/CD son reales y están listos para ser utilizados en la plataforma: su sintaxis fue validada con un analizador YAML, y los pasos que el pipeline ejecutaría se corrieron localmente con los mismos comandos, obteniéndose las salidas que se muestran como evidencia. Las funciones que solo existen en la interfaz web (aprobaciones, tableros, informes visuales) se describen como parte del funcionamiento de la plataforma y se identifican como tales.

2. Marco conceptual: versionamiento y plataformas en la nube

2.1 Control de versiones y Git

Un sistema de control de versiones (VCS) registra la evolución de un conjunto de archivos a lo largo del tiempo. Git, creado por Linus Torvalds en 2005, es un VCS distribuido: cada copia del repositorio contiene el historial completo, y las operaciones de confirmación y consulta de historial se realizan localmente. La colaboración se logra sincronizando repositorios mediante push y pull.

Los conceptos que se usarán en las demostraciones son:

  • Repositorio: base de datos de objetos que contiene el historial.
  • Commit: instantánea inmutable del proyecto, identificada por un hash SHA-1/SHA-256, con autor, fecha y mensaje.
  • Rama (branch): puntero móvil a un commit; permite líneas de trabajo paralelas.
  • Remoto: copia del repositorio alojada en un servidor (GitLab.com, Bitbucket.org, etc.).
  • Etiqueta (tag): marca fija de una versión, por ejemplo v1.0.0.

2.2 Qué aporta una plataforma en la nube

Git por sí solo no resuelve la colaboración a escala. Las plataformas en la nube añaden:

CapacidadDescripción
Alojamiento remotoServidor siempre disponible con respaldo, control de acceso y alta disponibilidad.
Revisión de códigoMerge Requests (GitLab) y Pull Requests (Bitbucket): propuesta de cambios con discusión en línea, aprobaciones y fusión controlada.
Protección de ramasReglas que impiden escribir directamente en ramas estables y exigen revisiones y comprobaciones previas.
CI/CDEjecución automática de compilación, pruebas y despliegue definida como código.
TrazabilidadHistorial auditable de quién cambió qué, cuándo y con qué resultado.
Gestión de trabajoIncidencias, tableros y su vínculo con las confirmaciones de código.

3. GitLab

3.1 Qué es GitLab

GitLab es una plataforma de DevOps que reúne en una sola aplicación el control de versiones Git, la integración y entrega continua (CI/CD), el registro de contenedores y paquetes, el análisis de seguridad, la gestión de incidencias y tableros, la documentación (wiki) y el alojamiento de sitios estáticos. Su propuesta de valor es sustituir una cadena de herramientas por una única plataforma, evitando integraciones externas y manteniendo una sola interfaz, un solo modelo de permisos y un solo historial de auditoría.

AspectoDetalle
EmpresaGitLab Inc. (empresa pública, cotiza en NASDAQ con el símbolo GTLB).
OrigenProyecto iniciado en 2011 por Dmitriy Zaporozhets y Valery Sizov; la empresa se funda en 2014 con Sid Sijbrandij como cofundador.
LicenciaModelo open core: Community Edition (CE) bajo licencia MIT y Enterprise Edition (EE) bajo licencia propietaria (código visible, uso restringido).
Formas de usoGitLab.com (SaaS), Self-Managed (autoalojado con paridad funcional, incluso en redes aisladas) y GitLab Dedicated (SaaS de un solo inquilino).
ImplementaciónRuby on Rails para la aplicación principal; Go para los componentes de alto rendimiento (Gitaly, Runner, Workhorse, Shell, Pages); Vue.js en el frontend; PostgreSQL y Redis como almacenes de datos.
Cuota de mercado SCMAproximadamente 16 % (frente al 68 % de GitHub y el 4 % de Bitbucket, según estimaciones de 2026).

GitLab no es un único programa: es un conjunto de servicios que se despliegan juntos (paquete Omnibus, contenedor Docker o gráficos de Helm sobre Kubernetes). Los componentes principales son:

El Runner merece atención porque es quien ejecuta el pipeline. Admite varios ejecutores: shell (rápido, sin aislamiento), docker (aislamiento por contenedor, el estándar), kubernetes (un pod por job, con escalado elástico), docker-autoscaler e instance. Un punto económicamente relevante: los runners autoalojados no consumen los minutos de cómputo de la suscripción.

3.3 Cómo funciona GitLab

El ciclo de trabajo típico sobre GitLab es el siguiente:

1. RamaSe crea una rama corta desde main
→
2. PushSe publica la rama en el remoto
→
3. Merge RequestSe abre el MR; el pipeline se dispara solo
→
4. RevisiónAprobaciones, comentarios y reglas obligatorias
→
5. FusiónMerge a main con el pipeline en verde
→
6. DespliegueEntornos y etiqueta de versión
  • Merge Requests (MR). Cada propuesta de cambio se discute en línea: comentarios por línea de código, sugerencias aplicables, hilos resueltos y aprobaciones. Se pueden exigir aprobaciones por rol o por propietario de código (CODEOWNERS, en Premium y Ultimate) y aplicar merge trains para serializar integraciones sin romper la rama principal.
  • Pipelines. Se declaran en el archivo .gitlab-ci.yml de la raíz del repositorio. Se organizan en etapas (stages) y jobs. Incluyen funciones avanzadas como el grafo de dependencias needs (permite que un job no espere a toda su etapa), la inclusión de plantillas compartidas (include, extends), pipelines padre‑hijo y pipelines multicitados entre proyectos.
  • Permisos y ramas protegidas. Los roles de proyecto son Guest, Reporter, Developer, Maintainer y Owner. Las ramas protegidas definen quién puede hacer push, force push o fusionar.
  • Push options. Desde la consola se puede pedir la creación del MR: git push -o merge_request.create -o merge_request.target=main origin feature/login. Es una capacidad exclusiva de GitLab entre las dos plataformas comparadas.

3.6 Ventajas y desventajas de GitLab

Ventajas
  • Plataforma única: repositorios, CI/CD, registros, seguridad y gestión del trabajo en un solo lugar; menos herramientas que integrar.
  • CI/CD maduro: dependencias entre jobs (paralelismo), inclusión de plantillas compartidas, merge trains y pipelines padre‑hijo.
  • Autoalojamiento con paridad: la versión autoalojada ofrece las mismas funciones que la nube, incluso en redes aisladas; clave para soberanía de datos.
  • Seguridad integrada: análisis estático y dinámico, dependencias y contenedores sin herramientas de terceros.
  • Registros incluidos: imágenes y paquetes por proyecto.
  • Código abierto (CE, MIT): permite auditar y autoalojar gratuitamente.
  • Control de aprobaciones: reglas por propietario de código y políticas obligatorias.
Desventajas
  • Curva de aprendizaje alta: interfaz densa y muchos conceptos (etapas, entornos, reglas, agentes).
  • Coste: el plan Premium (29 USD) es ocho veces más caro por usuario que el Standard de Bitbucket.
  • Consumo de recursos: el autoalojado exige bastante memoria y mantenimiento especializado.
  • Nivel gratuito limitado en la nube: 5 usuarios por grupo y solo 400 minutos de cómputo al mes.
  • Rendimiento percibido: la interfaz puede resultar más pesada que la de plataformas más simples.
  • Integración con Jira menos profunda que la nativa de Bitbucket.
  • Funciones de IA facturables por créditos, con coste variable.

4. Bitbucket

4.1 Qué es Bitbucket

Bitbucket es el servicio de alojamiento de repositorios Git de Atlassian. Su diferencial no es competir en comunidad ni en amplitud de funciones, sino conectar el código con el resto del ecosistema Atlassian: las incidencias viven en Jira, la documentación en Confluence y el seguimiento de despliegues se refleja automáticamente en ambos. Está orientado a equipos corporativos que ya utilizan esas herramientas.

AspectoDetalle
EmpresaAtlassian (NASDAQ: TEAM).
OrigenCreado en 2008 por Jesper Nøhr, inicialmente centrado en Mercurial; adquirido por Atlassian en septiembre de 2010. El soporte de Mercurial finalizó el 1 de julio de 2020, por lo que hoy es exclusivamente Git.
LicenciaPropietaria. El servicio en la nube es cerrado; la versión autoalojada (Data Center) requiere licencia comercial.
Formas de usoBitbucket Cloud (SaaS gestionado por Atlassian) y Bitbucket Data Center (autoalojado, con clúster activo‑activo).
ImplementaciónLa nube es una plataforma SaaS cerrada de Atlassian (originalmente escrita en Python/Django y hoy sobre la plataforma Java de Atlassian); Data Center es un producto Java con clúster sobre Hazelcast.
Cuota de mercado SCMAlrededor del 4 %.

4.3 Cómo funciona Bitbucket

1. RamaSe crea una rama corta desde main
→
2. PushSe publica la rama en el remoto
→
3. Pull RequestEl PR se crea desde la interfaz web
→
4. Merge checksMínimo de revisores y build correcto
→
5. FusiónMerge a main
→
6. DespliegueSteps por entorno con disparo manual
  • Pull Requests (PR). Revisión en línea con comentarios, tareas pendientes, revisores por defecto y comprobaciones de fusión (merge checks). En el plan Free y Standard las comprobaciones son recomendaciones; en Premium pueden hacerse obligatorias.
  • Pipelines. El archivo bitbucket-pipelines.yml define secciones default, branches, pull-requests y tags, cada una con una lista secuencial de steps. Los steps reutilizables se declaran en definitions mediante anclas YAML (&nombre / *nombre). No existe dependencia selectiva entre steps ni inclusión de archivos externos.
  • Permisos. Se definen a nivel de espacio de trabajo, proyecto, repositorio, rama y entorno, con restricciones de rama y revisores por defecto.
  • Autenticación. Las contraseñas de cuenta y las app passwords fueron retiradas: desde el 28 de julio de 2026 el acceso por HTTPS exige API tokens con permisos específicos o access tokens; también se admite SSH.
Cambios disruptivos de Bitbucket en 2026
  • Issues y Wikis nativos retirados: los datos se eliminaron a mediados de agosto de 2026; Atlassian dirige a Jira para las incidencias y a Confluence para la documentación. Bitbucket deja de ser una solución autosuficiente de planificación.
  • App passwords eliminados (28 de julio de 2026): toda automatización que usaba contraseñas de aplicación debe migrarse a API tokens con permisos.

4.6 Ventajas y desventajas de Bitbucket

Ventajas
  • Integración nativa con Jira y Confluence: enlaces automáticos, cambios de estado y seguimiento de despliegues.
  • Precio competitivo: 3,65 USD por usuario en Standard, el más bajo de los planes de pago analizados.
  • Curva de aprendizaje baja: configuración simple y revisión muy directa.
  • Nivel gratuito útil: repositorios privados ilimitados para equipos de hasta 5 personas.
  • DATA Center con clúster activo‑activo para alta disponibilidad autoalojada.
  • Controles empresariales accesibles en Premium: IP permitidas, doble factor obligatorio, comprobaciones de fusión forzosas.
  • Ecosistema de Pipes que cubre funciones no nativas.
Desventajas
  • CI/CD menos potente: sin dependencias selectivas, sin plantillas compartidas y sin merge trains; ejecución estrictamente secuencial.
  • Sin seguridad nativa: depende de herramientas externas.
  • Sin registro completo de contenedores y paquetes.
  • Dependencia del ecosistema Atlassian: sin Jira y Confluence la plataforma pierde buena parte de su valor.
  • Retiro de Issues y Wikis (2026): obliga a migrar y a pagar otras herramientas.
  • Nivel gratuito muy limitado en CI/CD: solo 50 minutos de compilación al mes.
  • Menor paridad entre la nube y la versión autoalojada.
  • Sin alojamiento de sitios estáticos ni funciones de IA tan amplias como las de la competencia.

6. Ejemplo 1 — Demostración con GitLab

6.1 Descripción del ejemplo

Se construyó el proyecto NotasApp: un módulo Python para el cálculo de notas académicas con validación de rangos, promedio aritmético, promedio ponderado y decisión de aprobación. El proyecto no requiere dependencias externas (solo la biblioteca estándar), de modo que puede ejecutarse en cualquier equipo o contenedor, y cuenta con 16 pruebas unitarias.

Sobre ese proyecto se aplicó el flujo de trabajo de GitLab Flow con ramas cortas por funcionalidad y Merge Requests, junto con un pipeline declarado en .gitlab-ci.yml con tres etapas: build → test → deploy.

Objetivo del ejemplo Demostrar, con evidencia real, (a) que el pipeline detecta automáticamente un error antes de integrar el cambio, (b) que el despliegue queda restringido a la rama principal y a una aprobación manual, y (c) qué nivel de complejidad exige la configuración de GitLab para lograr ese control.

El módulo principal

def promedio_ponderado(notas, pesos):
    """Calcula el promedio ponderado de las notas según sus pesos."""
    if len(notas) != len(pesos):
        raise NotaInvalidaError("La cantidad de notas y de pesos debe coincidir")
    if sum(pesos) <= 0:
        raise NotaInvalidaError("La suma de los pesos debe ser mayor que cero")
    total = sum(validar_nota(n) * p for n, p in zip(notas, pesos))
    return round(total / sum(pesos), 2)

Fragmento final de src/notas.py. Las dos validaciones y el redondeo fueron añadidos durante la demostración a raíz de un fallo detectado por las pruebas.

6.3 El pipeline de GitLab

# .gitlab-ci.yml - Pipeline CI/CD de GitLab para NotasApp (demostración)

stages:
  - build
  - test
  - deploy

default:
  image: python:3.12-slim

variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.pip-cache"

# Caché compartida entre jobs, invalidada cuando cambia requirements.txt
cache:
  key:
    files:
      - requirements.txt
  paths:
    - .pip-cache/

# ------------------------------- BUILD -------------------------------
build:
  stage: build
  script:
    - python -m pip install --cache-dir .pip-cache -r requirements.txt
    - python -m compileall -q src/
  artifacts:
    name: "build-$CI_COMMIT_SHORT_SHA"
    paths:
      - src/
    expire_in: 1 week

# -------------------------------- TEST -------------------------------
test:unitarias:
  stage: test
  needs: ["build"]              # DAG: arranca sin esperar otros jobs de 'test'
  script:
    - python -m unittest discover -s tests -v
  artifacts:
    when: always
    paths:
      - tests/
    expire_in: 3 days

test:estilo:
  stage: test
  script:
    - python -m pip install ruff
    - ruff check src/

# ------------------------------- DEPLOY ------------------------------
deploy:staging:
  stage: deploy
  needs: ["test:unitarias", "test:estilo"]
  environment:
    name: staging
    url: https://staging.notasapp.example.com
  script:
    - python scripts/deploy.py staging
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

deploy:produccion:
  stage: deploy
  needs: ["test:unitarias"]
  environment:
    name: produccion
    url: https://notasapp.example.com
  script:
    - python scripts/deploy.py produccion
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
      when: manual              # requiere aprobación manual en la interfaz
    - when: never

6.6 Análisis del ejemplo de GitLab

Lo que el ejemplo demuestra a favor
  • Control fino del flujo: la palabra clave needs permite que test:unitarias arranque sin esperar a test:estilo, algo imposible en la lista secuencial de Bitbucket.
  • Reglas expresivas: rules con comparación de variables evita desplegar desde una rama de trabajo.
  • Entornos con identidad: environment define nombre y URL, y la plataforma conserva el historial de despliegues y permite revertir.
  • Artefactos y caducidad: artifacts con expire_in y when: always garantiza que los resultados se conserven incluso cuando el job falla, justo lo necesario para diagnosticar el error del ejemplo.
  • Caché inteligente: la clave derivada de requirements.txt invalida la caché solo cuando cambian las dependencias.
  • Creación del MR desde la consola: reduce pasos manuales en el flujo diario.
Lo que el ejemplo evidencia en contra
  • Densidad de configuración: 76 líneas y nueve claves de nivel superior para un proyecto mínimo. Esa potencia se paga en tiempo de aprendizaje.
  • Dependencia de la interfaz para cerrar el ciclo: la aprobación manual y las reglas de aprobación se gestionan en la web, lo que añade un paso humano.
  • Mayor consumo de recursos: el job de estilo descarga herramientas en cada ejecución si no se cachean; optimizar el pipeline exige conocimiento adicional.
  • Coste: en la nube, cada minuto consumido cuenta sobre los 400 del plan gratuito, salvo que se usen runners propios.
  • Ruido por artefactos: el propio ejemplo mostró que sin un .gitignore cuidado se pueden versionar archivos generados como __pycache__.

# bitbucket-pipelines.yml - Pipeline CI/CD de Bitbucket para NotasApp

image: python:3.12-slim

definitions:
  caches:
    pip-cache: /root/.cache/pip        # caché de dependencias reutilizable

  steps:                               # steps reutilizables mediante anclas YAML (& / *)
    - step: &build
        name: Compilar
        caches:
          - pip-cache
        script:
          - python -m pip install --cache-dir /root/.cache/pip -r requirements.txt
          - python -m compileall -q src/
        artifacts:
          - src/**

    - step: &test
        name: Pruebas unitarias
        caches:
          - pip-cache
        script:
          - python -m unittest discover -s tests -v
        artifacts:
          - tests/**

    - step: &estilo
        name: Revisión de estilo
        caches:
          - pip-cache
        script:
          - python -m pip install ruff
          - ruff check src/

pipelines:
  # Se ejecuta en cualquier push que no coincida con una regla más específica
  default:
    - step: *build
    - step: *test

  # Pull Requests: además del build y las pruebas, exige revisión de estilo
  pull-requests:
    '**':
      - step: *build
      - step: *test
      - step: *estilo

  # Rama principal: incluye despliegues a los entornos
  branches:
    main:
      - step: *build
      - step: *test
      - step: *estilo
      - step:
          name: Desplegar en Staging
          deployment: staging
          script:
            - python scripts/deploy.py staging
      - step:
          name: Desplegar en Producción
          deployment: production
          trigger: manual            # requiere aprobación manual en la interfaz
          script:
            - python scripts/deploy.py production

7.6 Análisis del ejemplo de Bitbucket

Lo que el ejemplo demuestra a favor
  • Simplicidad: tres claves de nivel superior (image, definitions, pipelines) frente a las nueve de GitLab.
  • Organización declarativa por evento: default, pull-requests y branches expresan la política sin condicionales.
  • Reutilización con anclas YAML: los tres steps se definen una vez y se referencian con *build, *test, *estilo, evitando duplicación.
  • Menos configuración para el mismo resultado: 67 líneas frente a 76 con funcionalidad equivalente.
  • Despliegue por entorno sencillo: la clave deployment y trigger: manual se leen sin conocer reglas de expresión.
Lo que el ejemplo evidencia en contra
  • Ejecución secuencial obligatoria: no existe needs, por lo que el estilo esperaría aunque las pruebas pudieran correr antes; el pipeline completo tarda más.
  • Sin plantillas compartidas: las anclas YAML solo funcionan dentro del mismo archivo; reutilizar configuración entre repositorios depende de Pipes o de copiar el archivo.
  • Menos control sobre el almacenamiento de resultados: los artefactos no admiten reglas de conservación ni informes de prueba nativos.
  • Sin URL de entorno ni reversión nativa asociada al despliegue.
  • Dependencia de la interfaz para abrir el PR y, en planes inferiores, para que las comprobaciones de fusión sean efectivas.
  • 50 minutos gratuitos al mes: con este proyecto consumiría ~2 minutos por push, es decir, unos 25 pushes antes de tener que pagar.

Interpretación: para un proyecto pequeño ambos son suficientes y el resultado funcional es idéntico. La diferencia se manifiesta al crecer: cuantos más módulos, entornos y equipos, más pesa la falta de paralelismo, de plantillas compartidas y de informes nativos en Bitbucket; y cuanto más pequeño y presupuestado sea el equipo, más pesa el coste y la complejidad de GitLab.

9. Ventajas y desventajas de una plataforma sobre la otra

9.1 Dónde GitLab es claramente superior

Ventaja de GitLabPor qué es relevante

Una sola plataformaEvita integrar y pagar herramientas separadas de registro de imágenes, análisis de seguridad y planificación.

9.3 Resumen ejecutivo de la comparación

En una frase por plataforma GitLab: máxima capacidad, control y autonomía (incluido el autoalojamiento), al precio de mayor complejidad y mayor coste por usuario.
Bitbucket: mínima fricción y menor coste, integrado de forma insuperable con Jira, a cambio de un CI/CD más limitado, ausencia de seguridad y registros nativos y dependencia del ecosistema Atlassian, que en 2026 se redujo aún más con el retiro de las incidencias y las wikis propias.

10. Conclusiones y recomendaciones

10.1 Conclusiones

  1. Las dos plataformas resuelven el problema central del versionamiento en la nube: alojan repositorios Git, gestionan permisos, permiten revisar código y automatizan pruebas y despliegues. Con el mismo proyecto se obtuvo el mismo resultado funcional: 16 pruebas correctas, versión etiquetada y despliegue controlado.
  2. Las diferencias aparecen en el gobierno del proceso, no en el resultado. GitLab ofreció paralelismo entre tareas, condiciones expresivas, entornos con reversión e informes nativos; Bitbucket resolvió lo mismo con menos líneas y menos conceptos, pero de forma secuencial y con menos control.
  3. El CI/CD de GitLab es más potente y el de Bitbucket más sencillo. La evidencia es medible: 5 jobs con grafo de dependencias frente a 3 steps secuenciales, y 9 claves de configuración frente a 3.
  4. El coste es la diferencia más contundente. El plan de entrada de pago de GitLab cuesta unas ocho veces más por usuario que el de Bitbucket, aunque incluye registro de contenedores, seguridad y planificación que en Bitbucket habría que contratar aparte.
  5. La integración con Jira es el argumento decisivo de Bitbucket. Si la organización ya gestiona su trabajo en Jira y su documentación en Confluence, la ventaja de Bitbucket es difícil de igualar; si no, su valor disminuye notablemente, sobre todo tras el retiro de sus incidencias y wikis nativas en 2026.
  6. La seguridad y los registros nativos son exclusivos de GitLab entre las dos opciones analizadas; en Bitbucket se depende de herramientas de terceros, lo que añade coste y complejidad de integración.
  7. El autoalojamiento es el terreno donde GitLab no tiene competencia dentro de esta comparación: la Community Edition, bajo licencia MIT, permite operar una plataforma completa sin coste de licencia, algo imposible con Bitbucket.
  8. La autenticación obliga a actualizar automatizaciones. Con la desaparición de las contraseñas de aplicación de Bitbucket (julio de 2026), cualquier script que usara HTTPS debe migrar a API tokens; en GitLab el uso de Personal Access Tokens o claves SSH ya era la práctica habitual.

10.2 Recomendaciones

Si su situación es…Plataforma recomendada y razón
Ya usa Jira y Confluence y el presupuesto es limitadoBitbucket. La integración es inmediata y el coste por usuario es el más bajo; complete con Pipes lo que no es nativo.
Equipo pequeño (≤ 5) con proyecto privado sencilloBitbucket Free si el uso intensivo de CI/CD es esporádico; GitLab Free si necesita más minutos de cómputo (400 frente a 50) o publicar sitios estáticos.
Necesita integración y entrega continua avanzadas, varios entornos y equipos numerososGitLab. El grafo de dependencias, las plantillas compartidas y los entornos con reversión reducen tiempos y errores de publicación.
Debe autoalojar por normativa o soberanía de datosGitLab Self‑Managed (Community Edition gratuita o Enterprise), por su paridad funcional y su capacidad de operar en red aislada.
Requiere análisis de seguridad integrado y cumplimientoGitLab (la suite completa, en Ultimate), para evitar licencias y procesos separados.
Proyecto académico o de aprendizaje con énfasis en CI/CDGitLab, por su nivel gratuito más generoso en minutos de cómputo y por el valor formativo de su pipeline declarativo completo.

10.3 Recomendación metodológica final

Antes de decidir, se recomienda ejecutar una prueba de concepto con el proyecto real durante un ciclo de desarrollo completo: medir los minutos de CI/CD consumidos, el número de integraciones necesarias y el coste total para el tamaño de equipo definitivo. En esta comparación, la verificación de precios resultó indispensable: durante la investigación se encontraron cifras distintas entre las propias páginas de Atlassian, lo que confirma que los valores deben confirmarse antes de cualquier decisión presupuestal.
